# Super OI Simulator HTML 可玩战斗原型实施计划

> 本计划基于 `docs/GAME_DESIGN.md` 的战斗原型范围，目标是交付一个无需账号、服务器或构建服务，直接在浏览器打开即可游玩的单机战斗页面。

## 1. 目标与边界

### 1.1 本阶段目标

完成一个可重复、可观察、可重玩的小型战斗原型：

- 玩家从 6 名学生中选择 3 名，并放入 `A1`、`A2`、`A3`；
- 玩家可以交换站位，但战斗开始后不手动操作；
- 队伍自动挑战固定的多道题目；
- 页面显示回合、行动阶段、题目进度、学生精力、专注值、技能和事件日志；
- 玩家可以开始战斗、暂停/继续、单步执行、重新开始和调整战斗速度；
- 战斗结束后显示胜利、失败、通过题目数和关键统计；
- 相同配置与种子必须产生相同的事件日志和结局。

### 1.2 明确不做

本阶段不实现：

- 招生、货币、商店、背包、升级、突破和账号存档；
- 多人匹配、排行榜、服务器结算和实时同步；
- 协作解题、装备、天赋、随机事件和复杂学生关系；
- 后端 API、数据库和登录系统；
- 需要额外服务才能运行的开发环境。

这些内容保留到战斗原型稳定后的单机纵切片和异步多人版本。

## 2. 技术方案

### 2.1 运行方式

采用浏览器原生技术，不引入框架作为首版运行依赖：

- `index.html`：页面入口；
- `src/`：ES Module 格式的 JavaScript 战斗逻辑和界面逻辑；
- `styles/`：普通 CSS；
- `assets/`：可选的 SVG 图标和字体声明；
- 直接双击 `index.html` 可以打开基础玩法。

如果浏览器限制 `file://` 下的模块加载，则提供一个无配置的静态服务器命令作为开发辅助；玩法本身不得依赖服务器接口。

### 2.2 逻辑分层

战斗逻辑必须与 DOM 解耦：

```text
数据配置
  -> 战斗状态
  -> 纯函数结算内核
  -> 有序事件日志
  -> 页面状态渲染
```

建议模块：

- `src/data.js`：学生、技能、题目和关卡配置；
- `src/rng.js`：固定种子的伪随机数；
- `src/combat/math.js`：`clamp`、能力差距、进度、伤害和辅助效果公式；
- `src/combat/engine.js`：回合、阶段、目标快照、原子结算和胜负判断；
- `src/combat/events.js`：事件类型和事件日志序列化；
- `src/app/state.js`：编队选择、站位和播放控制状态；
- `src/app/render.js`：根据状态渲染页面，不在渲染函数中计算战斗；
- `src/app/main.js`：事件绑定和页面启动。

### 2.3 数据约束

所有战斗数值使用整数。学生能力使用百位尺度，题目进度和精力使用千位尺度。技能效果使用明确的基础值、倍率、目标倍率、持续回合数和上下限，不在页面组件中写死公式。

## 3. 界面与交互设计

### 3.1 视觉方向

采用白色背景为主的“清晰战术面板”风格：

- 背景：`#FFFFFF`；
- 正文：近黑色 `#171717`，普通文本对比度至少 4.5:1；
- 边框和分隔：浅灰 `#E5E5E5`；
- 主强调色：克制的金色 `#A16207`，仅用于主要行动、专注和胜利提示；
- 失败使用高对比红色，并同时显示文字或图标，不能只靠颜色传达；
- 字体优先使用 Inter，无法加载时回退到系统无衬线字体；
- 图标使用统一的 SVG 线性图标，不使用 Emoji 作为结构图标；
- 卡片圆角不超过 8px，避免卡片套卡片和大面积渐变。

### 3.2 页面布局

桌面端采用三栏信息层级，移动端改为单列：

```text
顶部：关卡名称 | 回合/上限 | 速度 | 重新开始
主区：A1/A2/A3 学生列 ↔ B1/B2/B3 题目列
侧区：当前行动说明 | 技能说明 | 事件日志
底部：开始/暂停 | 单步 | 目标进度 | 战斗结算
```

核心战场必须在首屏可见。移动端优先显示当前行动者、三名学生、三道活动题目和主要控制，其余日志可折叠，但不能产生横向滚动。

### 3.3 必备交互

- 编队：从学生池选择恰好 3 人；未满足条件时主按钮禁用并说明原因；
- 站位：使用可点击的交换控件完成位置调整，同时支持键盘操作；
- 开始：开始前显示关卡目标和固定随机种子提示；
- 播放：暂停、继续、单步、速度 `0.5x/1x/2x/4x`；
- 日志：按回合和阶段展示“谁对什么目标造成了什么效果”；
- 反馈：题目完成、学生退出、爆发技能和终局必须有文字状态与短时视觉反馈；
- 可访问性：所有按钮有可见文字或 `aria-label`，焦点环可见，支持 `prefers-reduced-motion`。

### 3.4 动效约束

只使用表达因果关系的动效：进度条变化、伤害数字、当前阶段高亮和完成状态切换。普通过渡控制在 150--300ms，避免布局位移；开启减少动态效果时，保留状态变化但移除位移动画。

## 4. 分阶段实施任务

### Task 1：建立可直接打开的页面骨架

- [ ] 创建 `index.html`、`styles/base.css` 和 `src/app/main.js`；
- [ ] 加入 viewport、语义化标题、主内容区域和无障碍跳转链接；
- [ ] 先渲染静态的学生列、题目列、控制栏和日志区；
- [ ] 验证 375px、768px、1024px 和 1440px 宽度下无横向滚动。

### Task 2：实现战斗数据与公式

- [x] 定义 6 名学生、至少 6 道题目和一个关卡配置；
- [x] 实现能力差距、基准进度、技能进度、题目伤害和辅助效果公式；
- [x] 实现整数四舍五入、上下限和题目剩余进度截断；
- [x] 为每个技能声明类别、目标规则、相关能力和效果参数。

### Task 3：实现确定性战斗内核

- [ ] 实现 `A1 -> B1 -> A2 -> B2 -> A3 -> B3` 阶段顺序；
- [ ] 实现候补题目在回合开始补位；
- [ ] 实现阶段开始快照、确定性并列选择和阶段末原子应用；
- [ ] 实现常规技能、专注值、爆发技能和精力为 0 时跳过行动；
- [ ] 实现题目完成、学生退出、回合上限和两种关卡目标；
- [ ] 输出包含回合、阶段、行动者、目标、效果和状态变化的事件日志。

### Task 4：把内核接入播放控制

- [ ] 用一个状态机管理 `编队 -> 准备 -> 战斗中 -> 结算`；
- [ ] 每次点击“单步”只推进一个结算阶段；
- [ ] 自动播放时按速度调度单步，不直接修改战斗状态；
- [ ] 暂停后不再产生新事件，继续时从当前事件位置恢复；
- [ ] 重新开始时恢复相同初始配置和种子。

### Task 5：完成战场渲染与反馈

- [ ] 学生显示能力摘要、精力条、专注条、当前技能和存活状态；
- [ ] 题目显示类型难度、完成进度、正对位置和候补状态；
- [ ] 当前行动者使用高亮和文本说明，不依赖颜色单独表达；
- [ ] 事件日志支持按回合折叠，自动播放时保持最新事件可见；
- [ ] 结算面板显示胜负、通过数量、剩余精力和重新挑战按钮。

### Task 6：测试与浏览器验证

- [ ] 为公式、目标选择、补位、爆发触发、状态持续和胜负条件编写自动测试；
- [ ] 验证同一种子运行两次时事件日志序列化结果完全一致；
- [ ] 使用至少 20 个手工编队/站位组合，检查结果和日志无异常；
- [ ] 在桌面和移动尺寸下实际点击完成一局；
- [ ] 检查键盘 Tab 顺序、焦点可见性、按钮禁用状态和减少动态效果模式；
- [ ] 构建一个 `npm run check` 或等价命令，统一执行语法检查和测试。

## 5. 推荐的首版内容

为了让试玩具有可比较性，首版固定配置建议包括：

| 学生 | 定位 | 常规技能 | 爆发技能 |
| --- | --- | --- | --- |
| 规划手 | 单体解题 | 攻击最低完成度题目 | 对单题造成高额进度 |
| 图论手 | 单体解题 | 攻击匹配度最高题目 | 同时攻击两题 |
| 结构手 | 防守辅助 | 恢复最低精力 | 全队恢复 |
| 数学手 | 难题解题 | 攻击最高难度题目 | 对最高难度题目造成高额进度 |
| 实现手 | 稳定输出 | 正对位置攻击 | 三题小幅推进 |
| 支援手 | 增益辅助 | 提高一名学生能力 | 全队短时增益 |

关卡至少包含简单单类型题、双类型题、三道同时活动题和候补题，以便站位、目标规则和群体技能确实产生差异。

## 6. 完成定义

当以下条件全部满足时，才进入单机纵切片：

1. 用户无需安装依赖或启动后端，打开网页即可开始一局；
2. 一局战斗可以完整开始、暂停、单步、重开和结算；
3. 同一随机种子生成相同事件日志；
4. 站位和队伍选择会对结果产生可解释的影响；
5. 关键规则均有自动测试，且测试通过；
6. 桌面和手机布局都能完成核心操作；
7. 页面没有未处理的异常、卡死的播放状态或无法关闭的弹层。

## 7. 交给 AI 的执行提示

让 AI 按 Task 1 到 Task 6 顺序执行，每完成一个 Task 都运行检查并报告：修改的文件、测试结果、当前可玩的入口和未解决问题。禁止一次性生成完整游戏；每个阶段都必须保留一个可运行版本，避免逻辑、视觉和数据问题同时堆积。
