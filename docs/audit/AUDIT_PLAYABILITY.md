# 审计报告：可玩性走查

本篇以一名新玩家的真实操作路径为主线（注册 → 编队 → 挑战 → 养成 → 竞技场），记录每个环节的体验问题。数值层面的死锁见 [AUDIT_BALANCE.md](AUDIT_BALANCE.md)，此处聚焦"玩起来"的层面。

---

## 1. 新手第一次小时体验走查

| 步骤 | 玩家所见 | 问题 |
| --- | --- | --- |
| 注册/登录 | 中文界面，流畅 | 无 |
| 进入主线关卡页 | 4 张关卡卡，3 张灰着"尚未解锁" | 无任何解锁条件说明（其实很简单：打赢前一关，但玩家打不赢，见下） |
| 点"开始挑战" | 战斗快照创建，跳转回放页自动播放 | 播放约 58 秒（72 步 × 800ms），无倍速按钮（§2.1），无"跳到结果" |
| 战斗结束 | "挑战失败"，完成 2/3 题 | **必然发生**：0% 胜率意味着新玩家首战必败且永远无法通关（AUDIT_BALANCE §1）|
| 失败后 | 页面停留在结算 | 无失败原因分析、无提升建议、无"去强化学生"引导；玩家不知道该干什么 |
| 自行探索到"训练与补给" | 强化面板 + 商店 + 签到 | 强化一次 +40，而差距需要数百点——没有进度感提示，玩家无法估算"还要练多久" |

**核心结论**：当前游戏的第一小时体验是"看一场必输的自动战斗 → 面对无解释的养成墙"。即使后续把数值调平（AUDIT_BALANCE §7），下面的反馈缺失问题仍会独立存在。

---

## 2. 【P1】战斗播放与结果获取的体验缺陷

### 2.1 【P1】无倍速控制、无跳过，单局观看成本近 1 分钟

- 播放控制器已支持 0.5/1/2/4 倍速（`src/app/state.js:5` 的 `PLAYBACK_SPEEDS` 与 `:118` 的 `setSpeed`），CSS 也写好了 `.speed-control/.speed-button` 样式（`styles/base.css:225-227`），但 `renderLiveBattle`（`src/app/router.js:102`）只有 播放/暂停/单步/重播 四个按钮，**没有任何代码调用 setSpeed**。
- 一场 chapter-1-4 战斗 = 18 回合 × 6 步 × 800ms ≈ **86 秒**；玩家重复挑战时这是纯粹的等待税。
- 服务端结算按钮（"开始回放并结算"）虽然可以立刻拿到结果，但页面同时开始播动画，两者关系未说明。

**建议**：补上倍速按钮组（数据、样式、状态机全部现成）；增加"直接结算"主按钮，把动画降级为可选。

### 2.2 【P1】战斗不可恢复、历史不可查

- 当前战斗只存在于内存 `this.battle`（`src/app/router.js:134`），刷新页面后 `applyHash` 的路由守卫（`:183`）静默跳回主线页，进行中的战斗无声消失；
- 服务端持久化了全部 `battle_records`（含事件日志），却没有提供列表查询接口，UI 也没有任何历史入口；
- 玩家无法回答"我昨天那把为什么输了""我对这关胜率多少"这类基本复盘问题。

**建议**：新增 `GET /api/v1/campaign/battles?limit=` 与战斗历史页；至少在刷新后保留最近一场的可恢复引用。

## 3. 学习曲线与机制可读性

游戏的核心策略维度（站位决定行动顺序与目标规则、专注值攒满自动爆发、辅助技能给队友充能）在 UI 中几乎不可见：

| 机制 | UI 呈现现状 | 缺口 |
| --- | --- | --- |
| 站位意义 | 名单页提示"拖动调整 A1/A2/A3 站位" | 从未说明站位影响什么；玩家不知道 A1 先手、正对 B 位互为攻防目标 |
| 专注爆发 | 学生详情里写着技能描述 | 战斗中学生头像旁有专注条但无"即将爆发"预告；supporter 给队友加专注会把别人瞬间顶到爆发线，这一联动完全无提示 |
| 目标规则 | 技能详情有文字（"剩余进度最低的题目"等） | 战斗中不显示当次行动选了哪个目标、为什么 |
| 题目反击逻辑 | 无 | "学生越不擅长这题，被打越疼"是核心张力，玩家只能从掉血隐约感知 |
| 失败诊断 | 无 | 结算只有 完成题数/回合/剩余精力 三个数字，无"差多少进度""谁先退场"等归因 |

**建议**：优先做两件事——(1) 结算页增加"最接近完成的题目还差 X 进度"一句话归因；(2) 主线页关卡卡片展示题目难度构成，让"推荐能力 550"变成可对照的具体数字。

## 5. 长线动力评估

- **目标层级单一**：4 个主线关 + 竞技场积分，无日常任务、成就、图鉴、收集进度等任何次级目标；签到是唯一登录理由。
- **养成终点可见且过近**：能力上限 2000、技能等级恒为 1（无升级系统）、学生数量靠招募缓慢扩张。跨过首关墙之后，玩家会在数周内触及所有系统的天花板。
- **重复挑战价值断裂**：奖励可无限刷（经济漏洞）与"打不过所以刷不了"并存，说明奖励结构从未按"重复游玩"设计过。
- **竞技场社交感为零**：对手是 UUID 片段（BUG-06）、无排行榜、无复仇/挑战记录，胜负不留痕迹。

**建议优先级**：先修 AUDIT_BALANCE §7 的数值与经济，再谈长线系统；当前阶段最有性价比的长线改动是"每日任务（签到 + 打 N 场 + 强化 N 次）"，能同时解决登录理由和首周资源缺口。

---

## 6. 表现力与性能

- 自动战斗的表现全靠文字事件流 + 数值条，无攻击动画/命中反馈；作为"模拟器"题材可接受，但配合 §2.1 的慢速播放，观感枯燥。
- 每 800ms 全页 innerHTML 重渲染导致滚动跳动、移动端发热（BUG-13），进一步降低观看意愿。
- 375px 移动端布局有专门覆盖与 E2E 断言（`e2e/single-player.spec.js` 末尾滚动宽度检查），响应式基础良好。

---

## 7. 可玩性总评

| 维度 | 评分（满分 5）| 说明 |
| --- | ---: | --- |
| 核心循环完整性 | 2 | 养成→战斗→奖励的环存在，但第一环就断（打不过→拿不到奖励）|
| 决策深度 | 2.5 | 站位/编队/养成路线有理论深度，但缺乏反馈让玩家感知决策生效 |
| 节奏 | 1.5 | 观战慢、养成周期以周计、无跳过手段 |
| 引导与反馈 | 1 | 无新手引导、无失败归因、错误消息英文 |
| 长线动力 | 1.5 | 系统天花板低、目标单一、社交缺失 |

修复顺序建议：数值死锁（BALANCE §7）→ 播放倍速/跳过 → 失败归因与基础引导 → 战斗历史 → 其余摩擦项随版本清理。
